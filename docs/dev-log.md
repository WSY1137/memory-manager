## 2026-10-09 · v2.0.1 触发词重构 + 名称修正

### 背景

v2.0.0 测试发现两个问题：
1. Skill 名称 `Memory Manager (记忆管理器)` 中的括号和中文导致系统匹配失败
2. 触发词都是系统术语（"记忆管家""记忆管理"），用户实际不会这么说

### 测试数据

| 测试 | 触发方式 | Skill 是否加载 | 输出格式 |
|---|---|---|---|
| 第1次 | 正常提问 | ❌ 不触发 | AI 正常回答，零污染 ✅ |
| 第2次 | "查记忆库" | ⚠️ 不确定 | 接近但不完全标准 |
| 第3次 | "memory-manager" | ✅ 正式加载 | 完全符合标准 ✅ |

第1次证明 v2.0.0 的核心设计成功了——正常提问不受记忆影响。第2次和第3次的问题通过触发词优化解决。

### 改动清单

1. **Skill 名称** — `Memory Manager (记忆管理器)` → `memory-manager`（纯英文，匹配目录名）
2. **触发词** — 从系统术语改为自然语言句式
3. **memory-config.md** — G1 触发闸门描述更新，版本号升至 v2.0.1

### 触发词对比

| 删除（用户不会说） | 新增（用户实际会说） |
|---|---|
| 记忆管家 | 查记忆库 |
| 记忆管理 | 查经验库 |
| 记忆库（太泛） | 记忆库有没有 |
| 经验库（太泛） | 经验库有没有 |
| 经验回顾（太正式） | 之前遇到过 |
| 之前有没有遇到过（太长） | 有没有相关经验 |

核心变化：每条触发词都是"动词+名词"的完整句式，而不是单独的名词。

### 验证

用户在新文件夹中测试，触发和输出正常。用户用 `memory-manager` 精确名称调用时 100% 正确加载和输出。

## 2026-10-09 · v2.0.0 定位转变：从"控制 AI 回答"到"独立记忆索引工具"

### 背景

v1.4.0 到 v1.4.1，又进行了 4 轮测试。结果：

| 版本 | 通过率 | 核心问题 |
|---|---|---|
| v1.4.0 第1测 | 1.5/3 | 记忆渗入主体 |
| v1.4.0 第2测 | 0.5/3 | 完全回到"记忆就是答案" |
| v1.4.0 第3测 | 2.5/3 | 用户说"附加"才做对了 |
| v1.4.1 第1测 | 2/3 | 末尾区块做到了，但开头仍提到记忆库 |

**结论**：在单次回答中"既有原生回答又有记忆附加"无法稳定实现。AI 一旦读到记忆文件，输出就会受影响。

### 核心决策：放弃融合，改为纯工具模式

用户提出了关键洞察：
> 既然调用必然导致融合，也许分两步可以得到更权威的信息。让 Skill 变成一个工具，为用户在准备新项目前提供历史经验的快速回顾。

这彻底改变了 Skill 的定位：

| 项 | v1.x（融合模式） | v2.0（工具模式） |
|---|---|---|
| 定位 | 在 AI 回答中融合记忆 | 独立记忆索引工具 |
| 触发 | 用户正常提问时 | 用户主动调用 |
| 输出 | 主体回答 + 记忆附加 | 只有记忆清单 |
| AI 影响 | 始终被污染 | 零污染 |
| 规则复杂度 | 5条/3条铁律/输出模板 | 只需"列出结果" |

### 新的工作流

```
用户正常提问 → AI 正常回答（不触发 Skill，零污染）

用户说"查记忆库" → Skill 触发 → 只输出记忆清单 → 用户自己决定怎么用
```

### 改动清单
- 4.1 从"记忆库检索"重命名为"经验回顾"
- 删除全部输出铁律/原则/格式约束
- description 去掉"记忆内容统一放在回答末尾"
- Role Definition 改为"记忆索引工具，不干涉 AI 正常回答"
- 新增触发词：经验回顾、之前做过类似的
- 输出格式简化为纯清单：标题 + 一句话摘要 + 来源

### 预期
- AI 正常回答完全不受记忆影响（根本不触发）
- 用户需要时主动调用，得到干净的清单
- Skill 规则大幅简化，执行率应该接近 100%
- 代价：需要用户主动调用（但这是唯一能保证零污染的方式）

## 2026-10-08 · v1.4.0 转向「完全附加模式」

### 背景
v1.2.0 到 v1.3.1，我们一直在努力让 Skill 遵守"原生为主、经验增值"的输出规范，加了自检清单、Hard Constraints、角色定义前置、功能置顶……但连续 4 轮测试，5 条规则几乎全失败。

### 核心发现
Skill 正文的详细规则执行力极低。AI 的行为模式是：
1. 触发了 Skill
2. 读了 description
3. **自己决定**去读记忆库文件
4. **自己组织**回答

SKILL.md 正文中的 Hard Constraints、输出模板、融合规则……可能根本没被读到，或者读到了但权重极低。

### 决策：放弃控制，回归简单
与其反复加规则、调结构、跟执行力较劲，不如换个思路：
- **接受现实**：Skill 正文的规则执行力有限
- **降低预期**：不要求记忆"融合+补充"，不要求比例控制，不要求命名统一
- **回归简单**：记忆就是附加内容，统一放在末尾，标注清楚来源

### 新的定位
记忆库检索 = 正常回答 + 末尾附加一个「📌 你的记忆库」区块。
- 主体回答不受记忆影响，该怎么答就怎么答
- 记忆内容集中在末尾，清晰分隔
- 标注来源 + 局限说明

### 改动清单
- Role Definition：从"原生为主，经验增值"改为"记忆是附加内容，不干涉主体回答"
- 输出原则：从 5 条 Hard Constraints 精简为 3 条简单原则
- 去掉"融合+补充"模式
- description 增加"记忆内容作为附加信息补充，不干涉主体回答"

### 预期
- 执行率应该会大幅提升（因为要求少了、简单了）
- 主体回答质量不受影响（本来就不该受影响）
- 用户能清晰区分"通用知识"和"个人经验"
- 代价：记忆内容和正文的关联度可能降低（但总比执行不出来好）

## 2026-10-08 · 记忆库数据丢失事故与恢复

### 事故概述
v1.1.0 → v1.2.0 更新过程中，同步文件时用 share 目录的模板版记忆库覆盖了全局目录的真实数据，导致 **8 条记忆全部丢失**。

### 原因分析
1. **同步方向搞反** — 把 share 目录（开发版/模板）的内容复制到了全局目录（真实数据）
2. **没有先检查目标文件内容** — 复制前没确认目标文件是否已有真实数据
3. **记忆库文件既是结构模板又是数据载体** — 模板和数据在同一个文件里，容易混淆

### 恢复过程
- 三个项目归档完整保留（ai-dev-ecosystem-doc、gaming-live-stream-cover、ai-agent-compare-study）
- 从归档中提炼出 **13 条记忆**（比丢失的 8 条还多，因为做了更完整的提炼）
- 分类：tech-stack 2 条、pitfalls 7 条、best-practices 5 条、patterns 1 条

### 教训与改进
1. **刚性规则新增「数据安全」** — 永远不要用模板覆盖已有真实数据
2. **批量同步前必须检查** — 目标文件有内容的，绝不直接覆盖
3. **初始化检查不重建已有文件** — 只补缺失的，不动已有的
4. **记忆库 = 数据，不是模板** — 开发时要区分清楚哪些是配置/模板文件，哪些是用户数据文件

## 2026-10-08 · v1.2.0 原生为主，经验增值

### 背景
v1.1.0 发布后进行了对照测试（Skill vs 原生回答），发现几个关键问题：

1. **记忆与通用知识混在一起** — 用户分不清哪些是个人经验、哪些是事实
2. **命名混乱** — "记忆库""知识库""经验库"三个名字混用
3. **缺少局限说明** — 没有告诉用户"记忆可能不全面"
4. **定位模糊** — 记忆到底是替代答案还是补充答案？不明确

### 核心决策

#### 1. 核心定位：原生为主，经验增值
这是 v1.2.0 最重要的调整。

| 项 | 说明 |
|---|---|
| 回答主体 | 模型通用知识（确保全面、准确、客观） |
| 记忆角色 | 增值补充 — 你踩过的坑、你验证过的方案、你的偏好习惯 |
| 比喻 | 记忆是"佐料"，不是"主菜" |
| 输出顺序 | 先原生回答 → 再记忆补充 |
| 记忆位置 | 回答后半部分，不喧宾夺主 |

**为什么这么定？**
- 对照测试证明：原生回答的广度和深度都很好，记忆没有显著提升整体质量
- 记忆的真正价值是"个人相关性" — 知道你做过什么、踩过什么坑
- 记忆内容少的时候，喧宾夺主反而会降低可信度
- 随着记忆库增长，增值效应会越来越明显，但"原生为主"的定位不变

#### 2. 三条刚性规则（从推荐升级为刚性）
从 v1.1.0 的"建议"升级到 v1.2.0 的"刚性规则"：

1. **命名统一** — 无论用户说"知识库""经验库""记忆库"，输出一律用"记忆库"
2. **分区呈现** — 记忆内容与通用知识必须分区，用小标题或分隔线明确分隔
3. **局限说明** — 只要引用了记忆，必须说明"记忆内容有限，可能不全面，仅供参考"

#### 3. 固定输出结构

```
【主体回答 — 通用知识，全面完整】
（先给完整的原生回答）

---

📌 来自你的记忆库（增值补充）
- 经验1：xxx  （来源：XX项目 / YYYY-MM-DD）
- 经验2：xxx  （来源：XX项目 / YYYY-MM-DD）

💡 提示：记忆内容基于你过往的项目经验，可能不全面，仅供参考。
```

### 改动清单
- SKILL.md：版本 1.1.0 → 1.2.0
  - 核心设计原则增加「原生为主，经验增值」
  - 刚性规则从 7 条增至 10 条（新增命名统一、分区呈现、局限说明）
  - 记忆库检索部分重写：明确核心定位、固定输出结构、分区呈现规则
  - 变更日志新增 v1.2.0 条目
- memory-config.md：版本号升级
- CHANGELOG.md：新增 v1.2.0 条目

### 后续待办
- v1.2.0 实测验证：命名是否统一？分区是否清晰？局限说明是否到位？
- 记忆库增长机制（如何让记忆库从 0 到 1）
- 归档流程的自动化触发探索

## 2026-10-08 · v1.1.0 改名与记忆影响原则

### 背景
v1.0.0 发布后，进行了实测验证，发现两个核心问题：

1. **触发率低（约 50%）** — "知识库"这个词和飞书知识库撞名，导致 Skill 误判或不触发
2. **记忆内容匮乏可能导致输出偏颇** — 记忆库只有几条数据时，如果 Skill 把记忆当答案输出，会比不给记忆更糟糕

### 核心决策

#### 1. 改名：知识库 → 记忆库
- **原因**：避免与飞书知识库等系统功能命名冲突
- **新名字**：记忆库（Memory Bank）
- **触发词优化**：增加"查记忆库""从记忆库里找""搜记忆库"等更独特的表达
- **影响范围**：SKILL.md、4 个记忆库文件、memory-config.md、CHANGELOG.md

#### 2. 重新定位：记忆是透镜，不是过滤器
| 维度 | 模型训练数据 | 用户记忆库 |
|---|---|---|
| 数量 | 万亿 token | 几条到几千条 |
| 广度 | 什么都知道一点 | 只知道你经历过的 |
| 角色 | 提供全面知识 | 提供你的视角 |
| 用法 | 直接回答 | 补充参考 |

**核心洞察**：记忆不是"更多知识"，而是"你的视角"。它让回答更像你，但不能让回答只剩你。

#### 3. 记忆影响原则（新增）
为防止记忆库内容匮乏导致输出偏颇，确立五条原则：
1. 记忆是参考，不是答案
2. 记忆有局限，要说明可能不全面
3. 正反都要提，引用了记忆里的方法也要说其他备选
4. 标注来源和置信度
5. 事实性问题不靠记忆，记忆只提供个人视角

#### 4. 来源标注规范（新增）
统一格式：`📌 来自你的记忆：[条目名]（XX项目 / YYYY-MM-DD）`
- 让用户清楚区分哪些是记忆、哪些是通用知识
- 标注位置自然，不破坏阅读流畅感

### 改动清单
- SKILL.md：版本 1.0.0 → 1.1.0，全文档"知识库"→"记忆库"，新增记忆影响原则和来源标注规范
- 4 个记忆库文件：标题说明补充"属于记忆库的一部分（原知识库，v1.1.0 改名）"
- memory-config.md：版本号升级
- CHANGELOG.md：新增 v1.1.0 条目
- 全局同步：~/.trae-cn/ 下所有文件同步更新

### 后续待办
- 触发率再测试（v1.1.0 触发词是否更准确）
- 记忆影响原则的实际效果验证
- 记忆库增长机制（如何让记忆库从 0 到 1）

## 2026-10-08 · v1.0.0 骨架搭建

### 背景

用户反馈 TRAE 的记忆功能内容很少，只有一两条。讨论后发现：
1. TRAE 原生记忆的自动提取能力有限，只识别非常明确的偏好
2. 没有项目归档机制，做完的项目知识就流失了
3. 没有跨项目的知识复用能力
4. 记忆管理缺乏可视化和系统化的体验

因此决定做一个**记忆管理器 Skill**，弥补 TRAE 原生记忆功能的不足。

### 开发目标

- 项目做完后，说一声就能自动归档沉淀
- 知识库能跨项目复用经验
- 记忆能自动/半自动整理
- 有统一的入口和可视化概览
- 质量可控，不浪费算力

### 架构设计

#### 五级记忆体系

```
L1 会话记忆 (topics.md)
  → L2 项目记忆 (project_memory.md)
    → L3 项目归档 (archive/*.md)
      → L4 全局偏好 (user_profile.md)
      → L5 知识库 (knowledge/*.md)
```

设计思路：层层筛选，越往上越精华。不是什么都记，而是有提炼的过程。

#### 六级闸门系统

为了解决"触发控制"和"质量保证"的问题，设计了六级闸门：

| 闸门 | 解决的问题 |
|---|---|
| G1 Trigger | 什么时候加载 Skill，避免误触发 |
| G2 Intent | 真的要做还是随口提 |
| G3 Quality | 这件事值不值得做（防止生成空洞内容） |
| G4 Process | 按多完整的流程走（繁简控制） |
| G5 Write | 能不能写入文件（写入保守度） |
| G6 Safety | 破坏性操作保护（安全底线） |

每道闸门有 strict/medium/loose 三档，还有快速预设。

#### 三级灵活度原则

为了解决"Skill 规则和 AI 原生推理打架"的问题：

- 🔴 刚性规则（Must）— 安全底线，绝对不能碰
- 🟡 推荐流程（Should）— 建议遵循，但有更好的做法可以偏离
- 🟢 可选建议（May）— 仅供参考，自由发挥

核心思想：**Skill 是默认剧本，不是铁律**。AI 可以灵活调整，但安全底线不能碰。

### 功能清单

**核心功能（5 个）**：
1. 项目归档 — 生成结构化归档文档，提炼经验
2. 知识库检索 — 跨项目搜索相关经验
3. 记忆整理 — 去重、合并、分类优化
4. 偏好复盘 — 从历史中提炼稳定偏好
5. 状态概览 — 统计仪表盘

**辅助功能（3 个）**：
1. 帮助信息 — 使用说明和命令速查
2. 健康检查 — 记忆系统完整性检测
3. 配置管理 — 对话中调闸门配置

### 技术选型

| 决策 | 方案 | 原因 |
|---|---|---|
| 实现形式 | TRAE 自定义 Skill（纯 Markdown） | 利用 TRAE 现有能力，零额外依赖 |
| 存储格式 | 纯 Markdown | 人类可读、易编辑、Git 友好 |
| 配置方式 | 独立配置文件（memory-config.md） | 配置驱动，用户不用改核心逻辑 |
| Skill 类型 | 全局 Skill | 记忆管理是跨项目的能力 |
| 知识库分类 | 4 大类（技术栈/踩坑/最佳实践/模式） | 平衡粒度，不粗也不细 |

### 踩坑记录

#### 1. Git 全局配置权限问题

**问题**：在 TRAE 沙箱中执行 `git config --global` 报错 `Permission denied`，因为沙箱不让写用户目录的 `.gitconfig` 文件。

**解决方案**：让用户手动在终端执行一次配置命令。

**经验**：TRAE 的命令执行是在沙箱里的，涉及用户全局配置的操作可能受限。

#### 2. GitHub MCP 权限不足

**问题**：`create_repository` 接口返回 403，提示 "Resource not accessible by integration"。

**解决方案**：改用浏览器手动创建仓库，然后用 `push_files` 接口推送代码（这个接口有权限）。

**经验**：GitHub 插件的权限范围有限，不是所有操作都能做。推送文件是 OK 的，但创建仓库不行。

#### 3. PowerShell 路径问题

**问题**：每次 `RunCommand` 后工作目录会重置，不是持久的。

**解决方案**：用 `cwd` 参数指定每次命令的工作目录，而不是依赖 `cd`。

**经验**：TRAE 的命令执行是无状态的，每次调用都是独立的。

## 2026-10-08 · v1.0.0 实测与 v1.1.0 规划

### 背景

v1.0.0 骨架搭好后，进行了第一次实测——验证知识库检索功能的有效性。

**测试方法**：对照组（无记忆）vs 实验组（有记忆），4 道题，双会话对比。

### 测试结果

#### 触发情况

4 道题中 2 道成功触发，触发率约 50%。

| 题目 | 是否触发 | 说明 |
|---|---|---|
| Q1：docx.js 常见坑 | ❌ 未触发 | "用知识库回答"触发词太弱，AI 直接搜网了 |
| Q2：文档生成工作流 | ✅ 触发 | 命中 docx.js 相关内容，质量不错 |
| Q3：AI 图像生成 | ✅ 触发 | 命中 AI 图像生成相关内容，质量很好 |
| Q4：工具评估方法 | ❌ 走偏 | "知识库"被理解为飞书知识库，去请求飞书授权了 |

#### 触发成功时的质量

- **Q2（文档工作流）**：独家内容命中 5/6，回答结构清晰，有代码示例，但没有标注来源。⭐⭐⭐⭐
- **Q3（图像生成）**：独家内容命中 4/4，有明确的来源标注（📌 来源：游戏直播封面项目），还做了合理扩展。⭐⭐⭐⭐⭐

### 关键发现

#### 发现 1：触发是小问题，价值才是大问题

触发率低可以通过优化触发词解决，但更根本的问题是：
**用了记忆管理器的输出，真的更好吗？**

对比结论：
- 对照组的回答已经很全面（AI 本身知识丰富）
- 实验组的价值不在于"知道更多"，而在于"知道你的具体经验"
- 记忆库的内容量永远不可能和大模型的训练数据相比
- 所以记忆系统的定位不应该是"补充知识"

#### 发现 2：命名冲突是个实实在在的问题

"知识库"这个词太通用了，和飞书知识库撞名，导致 Q4 完全走偏。
记忆管理器里的"知识库"需要改成更独特、更有辨识度的名字。

#### 发现 3：核心担忧——记忆匮乏导致输出偏颇

用户提出了一个非常关键的问题：
> Skill 数据库数据的匮乏，会不会导致输出的单一和偏颇？

这个担忧完全成立：
- 记忆库只有几条经验，覆盖面远不如模型的通用知识
- 如果 AI 过度依赖记忆库，反而会导致视野变窄
- 小样本经验被过度放大，可能变成路径依赖

### 重新定位：记忆是透镜，不是过滤器

经过讨论，对记忆系统的核心定位做了修正：

**记忆不是"更多知识"，而是"你的视角"。**

| 维度 | 模型训练数据 | 用户记忆库 |
|---|---|---|
| 数量 | 万亿 token | 几条到几千条 |
| 广度 | 什么都知道一点 | 只知道你经历过的 |
| 深度 | 浅而广 | 深而专（你的具体场景） |
| 作用 | 提供知识基础 | 提供上下文和偏好 |
| 可信度 | 可能有幻觉 | 你亲自验证过的 |

记忆系统的终极目标不是让 AI "知道更多"，而是让 AI "更懂你"。
懂你 = 在全面的信息里，帮你找到最适合你的那部分。

### v1.1.0 改进方向规划

#### 短期（马上可以改）

1. **触发词优化** — 把"知识库"改成更独特的名字，避免和飞书撞名
2. **来源标注标准化** — 所有从记忆引用的内容都统一标注格式
3. **记忆影响原则** — 明确记忆是佐料不是主菜，防止过度依赖

#### 中期

4. **置信度系统** — 每条记忆标注可靠程度（铁律/经验/假设/猜测/过时）
5. **静默检索模式** — 后台悄悄查，有结果自然融入，没有就不打扰
6. **记忆边界感** — 明确记忆该管什么、不该管什么

#### 长期

7. 记忆完全后台化
8. 记忆召回和生成本质融合

### 记忆影响原则（草案，待确认）

待用户确认后加入 SKILL.md：

1. 记忆是参考，不是答案 — 永远提供更全面的视角
2. 记忆有局限 — 说明"这是你之前的经验，可能不全面"
3. 正反都要提 — 说了记忆里的方案，也要说其他方案
4. 标注来源和置信度 — 让用户知道这条信息的分量
5. 事实性问题不靠记忆 — 客观事实用通用知识回答，记忆只提供个人视角

### 踩坑记录

#### 4. "知识库"命名冲突

**问题**：用户说"用知识库回答"，AI 理解成了飞书知识库，去请求飞书授权了，完全偏离记忆管理器的功能。

**原因**："知识库"是通用词，TRAE 系统内置了飞书知识库功能，优先级比自定义 Skill 高。

**经验**：Skill 的触发词和核心概念必须足够独特，避免和系统内置功能撞名。
